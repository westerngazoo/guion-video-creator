# Migration plan: the kit, the finishes and 3D

- **Status:** Proposed. The owner approved the direction on 2026-11-22. Each
  phase starts only after he OKs its requirement or spec.
- **Decision:** [ADR-0006](decisions/0006-layered-architecture-kit-and-finishes.md)
- **Repos:** guion-video-creator (gvc), rotorf-sico (rs), motoreel (mr),
  physics-lab (pl). All are under `~/projects`.

## Rules for every phase

1. **One concern per PR.** A move across repos is two PRs: the add in the
   library repo, then the switch-over and delete in rotorf-sico. They merge
   in that order (rotorf-sico `docs/infra.md` §2b: Cargo reads every path
   dependency's manifest, so the library must exist first).
2. **Byte identity is the gate.** `tools/golden-reels.sh` (rs) is green
   before and after, and its golden file is **never** regenerated by a
   migration PR. A moved function is moved **verbatim**: same operation
   order, same constants, same tessellation counts. Re-associating
   `a + b + c` or "tidying" a loop changes the last bit and the frame.
   Clean-ups come in a later PR that is allowed to change goldens, and that
   PR says so.
3. **Each moved piece carries its tests.** Wherever it lands, a moved piece
   brings an oracle test: the old function, copied as a test-only oracle and
   cited with its source commit, compared with `PartialEq` on `Prim2`.
4. **Sizes below are changed lines** (added + deleted), rough, across both
   PRs of the phase. The preferred size is 100–400 per PR and the ceiling is
   ~800 if atomic. Anything bigger is already split here.

## Phase 0 — Golden coverage first (prerequisite, added by this plan)

`tools/golden-reels.sh` today renders **4 reels, 12 frames**
(`erguido-inclinado`, `la-frenada`, `root-two-irrational`, `un-tic`).
`publicar/` holds **131 MP4s**, and phases 1–3 touch code used by dozens of
bins: 31 files in `fbf/motor` import `tablero_vs` or `vs_dibujo`, 35 import
`juguete`, and 32 files repo-wide use `luz`. Without wider coverage, "byte
identical" would be a hope, not a proof.

- rs: extend `REELS` to one entry per **Rust** reel bin whose output is in
  `publicar/` (the HTML+`setT` reels predate motoreel and are untouched).
  Add the brand assets: the PNGs `bin/marca` writes for computar,
  sobreviviente, maistro and fbf, hashed as decoded RGBA the same way the
  script already hashes frames.
- **Size:** ~150–250 (script plus the golden list). One PR.
- **Risk:** render time. Three frames per reel keeps it in minutes. A
  `--solo <bin>` flag lets a phase PR run the reels it touches first and
  the full set before merge.

## Phase 1 — Logo and watermark into the kit

The kit crate is born here, with the least risky pieces: machinery that is
already identical.

- **1a. Brand export machinery.** gvc: create `crates/guion-kit` (module
  `marca`), with a requirement in `docs/requirements/` first. Move, verbatim:
  - `ffmpeg`, `cargar`, `png_rgba`, `rgba_transparente`, `canvas`, `png`,
    `png_con_fondo`, `svg`, `renglones` and `mockup`. Sources:
    `computar/motor/src/bin/marca.rs`, `sobreviviente/motor/src/bin/marca.rs`,
    `maistro/motor/src/bin/marca.rs`. `mockup` gets the per-account
    differences as parameters; if a parameter cannot express one, that
    account keeps its own `mockup` for now.
  - The legibility check `dentro` and the constants `C` and `DENTRO`, from
    the three accounts' `src/marca.rs`.

  rs: the three `bin/marca.rs` and `src/marca.rs` call the kit.
  **Size:** gvc +350, rs −420/+60 ≈ **830**, so it splits into 1a-i (export
  helpers, ≈ 450) and 1a-ii (`mockup` and `dentro`, ≈ 380).
- **1b. The watermark and closing logo in reels.** Add the kit's
  watermark-at-size (1080, 150 and 80 px, the sizes the accounts write
  today). fbf's identical `logo` and `sello` in the four
  `fbf/motor/src/bin/top_*_goose.rs` move to one place. `rf_marca::rf::Rf::marca`
  (the 80 px watermark layer) stays put; it is already single.
  **Size:** ≈ 150.
- **Not in phase 1:** the other identical functions in the four `top_*`
  bins (`cuadro`, `casillas`, `cabecera`, `portada`, `version`) are fbf-only.
  They go to an fbf module in a separate small PR, not to the kit.
- **Risk:** low. The functions are byte-identical and move as they are.
  Brand PNGs are covered from phase 0.

- **Size:** 2a decouple ≈ 120; 2b `tablero` ≈ 750 (gvc +400 with tests, rs

- **Risk:** the unmerged `fbf/lote-2-vs-wip` branch (`vs_mitad.rs`,

## Phase 3 — The toy figure, the x-ray and the light

The largest move. It is split three ways and runs after phase 2, because
`vs_mitad` composes all three.

- **3a. Light.** `brand/rf-marca/src/luz.rs` (589 lines: cone, pool,
  vignette, `sombreado`, `sombreado_capsula`, halo) → `guion-kit::luz`. It is
  already account-neutral (colours arrive as `Rgb`). The account wrappers
  stay: `computar/motor/src/luz.rs` (`Placa` methods) and
  `sobreviviente/motor/src/luz.rs` (`haz`, `miembro`, `volumen`, `lampara`).
  **Size:** ≈ 750 (gvc +620, rs −589/+~60 across 32 files). It can split
  into geometry (cone, pool, vignette) and shading (`sombreado*`, halo) at
  ≈ 400 each.
- **3b. X-ray.** `juguete::rayos_x*` (9 functions), the sweep helpers from
  phase 2, and one parametrised `barrido_x`. The 13 bin-local copies are
  replaced only where their body equals the shared one (8 of them). The 5
  divergent ones keep local timings and call the kit with their own
  constants. **Size:** ≈ 500.
- **3c. The toy figure.** `juguete.rs` (939 lines: `Tonos`, `Forma`,
  `zoom`, `pintar`, `capsula`, `monito*`, `Escenario`) → `guion-kit::juguete`.
  The `Acabado { Capas, Suave }` enum moves as is; phase 5 replaces it.
  `monito_libre.rs` (wip branch) joins if merged by then.
  sobreviviente's `capsula` (12 segments) and `elipse` (48 sides) are **not**
  unified with the toy's (10 segments, 28 sides): that would move their
  frames. They become calls with an explicit segment count. **Size:** ≈ 1
  100, so it splits into shapes and `Forma`/`pintar` (≈ 450) and the
  figure (≈ 650).
- **Risk:** the highest of the plan. The functions use `atan2`, `cos` and
  `sin`, which are bit-stable on one machine but not across libm versions
  (motoreel `project-specifics.md`). Golden runs must happen on the same
  machine before and after a PR, and CI's golden needs a pinned image.

## Phase 4 — Physics to physics-lab

One model per PR, each into `physics-lab/mecanica` with its oracles. fbf
already depends on `mecanica`.

| PR | From (rs) | Lines | Note |
|----|-----------|-------|------|
| 4a | `fbf/motor/src/guia_profundidad.rs` | 230 | Already built on `mecanica::{maquina_humana, palanca}`. It needs the squat pose from `estilo_monito`, so 4d's pose part may come first |
| 4b | `fbf/motor/src/curl_tecnica.rs` | 423 | Uses `crate::curl::{G, LF}`. Reconcile with `mecanica::curl` and do not duplicate `G` |
| 4c | `fbf/motor/src/barra_rebote.rs` | 324 | A damped bar with steel constants. Needs a physics-lab requirement (a new area, not gym biomechanics only) |
| 4d | `fbf/motor/src/estilo_monito.rs` (model half: torques, levers, `pose`) | ~150 | The drawing constants stay in fbf |

- **Size:** each 300–600 including tests. Four PRs in pl, four switch-over
  PRs in rs (≈ 50 each).
- **Risk:** numeric drift. A model that moves must return the same `f64`
  bits, because the reel's frames depend on them. Byte-identity tests on
  the model outputs (and `golden-reels.sh`) gate each PR. physics-lab's
  wasm release profile (`opt-level = "z"`, LTO) does not affect the native
  build the motors use.

## Phase 5 — The finish trait with `Facetas`

- mr: implement **R-0017** (after the owner's OK and a spec): the
  surface, the material, the trait, and `Facetas` equal to rf-marca's
  `faceta`, `faceta_con_junta`, `velo`, `lambert` and `cuantizar`.
  **Size:** ≈ 700 (≈ 300 code, ≈ 400 tests), one PR.
- gvc: the kit's `juguete::pintar` paints through a finish.
  `Acabado::Capas` maps to `Facetas`. `Suave` maps to `Facetas` plus R-0016
  gradients, exactly as today. **Size:** ≈ 300.
- rs: rf-marca's `poly::{faceta, velo, lambert, cuantizar}` become thin
  calls to motoreel (or stay as oracles in tests). **Size:** ≈ 150.
- **Risk:** batch quantisation (R-0017 OQ-1). If a reel quantised two
  figures in one call, it must keep doing so.

## Phase 6 — Faceted 3D

- mr: **R-0018** (meshes, cull, painter's sort, finish). **Size:** ≈ 900,
  split into mesh, cull and sort (≈ 450) and finish integration, seams and
  the demo (≈ 450).
- gvc: the kit's low-poly generators (capsule, prism, faceted sphere) and
  a 3D toy built from them, used by **one new** reel only. Existing reels do
  not change. **Size:** ≈ 500.
- **Risk:** cyclic overlaps at joints (elbow, knee). The toy's parts must
  be split so no two faces cross (R-0018 §4).

## Phase 7 — `Pintura` pilot

- mr: a `Pintura` requirement (Hertzmann 1998 strokes, seeded by
  `(seed, surface id)`, anchored to the surface frame for temporal
  stability per Meier 1996), then its implementation. **Size:** ≈ 600.
- rs: one pilot reel in fbf, reviewed by `fisico` then `designer`. No
  existing reel changes.
- **Risk:** flicker. Strokes that are stable per frame but reseeded when
  a surface's id changes (a face culled, then back). The R-0017 AC7 test
  guards translation. Occlusion needs its own test in the `Pintura`
  requirement.

## Phase 8 — Real-time backend spike (the app)

A POC, not a product. It lives in `~/code/lab/YYYY-MM-fbf-app-tiempo-real`
with a hypothesis, success criteria and a kill date (global working
agreement for POCs).

- **Hypothesis:** the kit's description of one fbf scene (two toys, VS
  board, x-ray sweep) and one physics-lab model can be rendered at 60 fps
  on a mid-range phone, with no copy of either.
- **Success:** it builds for the chosen platform. It depends on `guion-kit`
  without the `motoreel` feature, and on `mecanica`, by path. A side-by-side
  with the motoreel frame is recognisably the same piece.
- **Size:** ≈ 800, throwaway.
- **Risk:** the seam fails. If the description needs motoreel types to be
  useful, ADR-0006 alternative 6 (the kit emits `Prim2`) wins, and the
  description is cut back.

## App: decisiones pendientes

The owner decides these before phase 8 starts.

### 1. Platform

| Option | For | Against |
|--------|-----|---------|
| **iOS + Android** | Where a gym user is, with the phone in hand | Two stores, two review processes, device fragmentation (Android GPUs) |
| **iOS first** | One target, a uniform GPU family, the simulator already in the toolchain | Leaves out Android, which is widely reported as the majority platform in Mexico (confirm with a current source before deciding) |
| **Web first (PWA)** | No store, one link from the Instagram bio, and physics-lab already ships Rust to wasm32 for its web lab | Weaker offline and sensor access. WebGPU support is still uneven across mobile browsers, so a WebGL2 fallback is likely |

### 2. v1 scope

What the first release must do decides the backend. Candidates:
- **a)** explain one exercise interactively (the reel, but you scrub and
  change the load);
- **b)** a rep counter or tempo coach using phone sensors;
- **c)** a workout log with the physics as commentary.

(a) needs the kit and the real-time backend. (b) needs sensors, not 3D.
(c) barely needs graphics. *Recommendation:* (a) alone, because it is the
only one that reuses what exists.

### 3. Real-time backend

| Option | For | Against |
|--------|-----|---------|
| **Bevy** (Rust, wgpu) | Same language as the whole stack: it can depend on `guion-kit` and `mecanica` by path, with no FFI. ECS fits "a description evaluated per frame". iOS, Android and web targets | Pre-1.0: breaking releases every few months. Mobile is less mature than desktop. Large binary and slow compiles. App UI (forms, lists, settings) is weak compared with native UI toolkits |
| **Native UI + Rust core** (SwiftUI / Jetpack Compose, with the kit and physics via UniFFI) | Best platform UI and store polish. The Rust core stays shared | Drawing has to be written twice (Metal/Canvas and Compose Canvas) or through a shared wgpu surface. Two UI codebases |
| **Flutter + Rust** (`flutter_rust_bridge`) | One UI codebase for both stores, mature tooling | A third language (Dart). The scene is drawn in Flutter's canvas, so the kit's pieces are re-implemented, not reused |
| **Web: wasm + WebGL2/WebGPU** (e.g. wgpu on the web, or a thin canvas renderer) | Reuses the physics-lab wasm pipeline. Zero install | The same platform trade-offs as above. Mobile browser performance limits are the main risk |
| **A lighter Rust renderer** (macroquad/miniquad) | Small, quick to build, runs on mobile and web | Small ecosystem. Less in the box for UI and 3D than Bevy |

*Recommendation:* decide platform and v1 scope first. If the answer is
"(a), iOS + Android", spike Bevy in phase 8, with the native-UI + Rust core
option as the fallback the spike is compared against. Bevy is the only
option where the app reuses the kit's Rust code directly instead of
re-implementing it.
